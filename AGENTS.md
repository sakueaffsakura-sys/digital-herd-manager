- System admin = `user_roles.role='administrador'`; admin data only via SECURITY DEFINER `admin_*` RPCs that check `private.has_role` — why: server-side authorization, never client flags.
- Selection lists fetch via `fetchAllRows` (1000-row chunks) — why: PostgREST caps responses at 1000 rows.
- Record forms share `loadFormRefs` and remount when their property/module scope changes — why: one cache contract prevents missing choices and stale editing targets.
- All record forms use typed references resolved to existing IDs before validation; categorical text normalizes to configured values and reference eligibility stays enforced — why: writing must preserve valid relationships and database constraints.
- Mount the shared Sonner Toaster once in the root layout — why: record validation errors and save confirmations must remain visible across every section.
- Tour page setup is separate from narration and waits for mounted targets — why: pausing speech must not reset examples or lose tab navigation.
- Request rate limiting is in-memory per worker in `src/start.ts` — why: cheap abuse protection; volumetric DDoS is handled by the hosting edge.
- Security events (rate-limit blocks, global spikes) are aggregated per worker in `src/lib/security-events.server.ts` and flushed to `eventos_seguranca` at most every 15s; admins read them via `admin_alertas` — why: attack visibility without the logger adding load during an attack.
- Yui support chat streams via server route `/api/yui` (`src/lib/yui.server.ts`, bearer-verified, per-user rate limit) and persists messages in `suporte_mensagens`; the guided tour preloads AI speech through the authenticated `/api/yui/voz` route with browser speech synthesis as fallback — why: keys stay server-side while the tour remains audible when AI speech fails.
- Yui's single-function lessons reuse filtered steps of the full guided tour — why: the same narration and target hints remain consistent without maintaining duplicate lesson scripts.
- Yui's optional chat wallpaper stores its active path in `configuracoes_sistema` and media in a private bucket readable and writable only by admins — why: private media and settings must not be exposed to other accounts.
- Site creator credits are stored as validated structured text in `configuracoes_sistema` and read into the About dialog only for admins — why: credits remain editable without exposing private settings to other accounts.
- Playwright auth restore writes the minted session with `localStorage.setItem(key, JSON.stringify(session))` — never `context.add_cookies`, and never splice the JSON into the script text as a bare object literal (it stores `[object Object]`, which reads as "session expired") — why: broken restore fakes an auth bug.
- Typed references are checked against property-scoped live rows before auto-creation, and unique conflicts re-read the winner; eligibility still applies — why: stale form caches and retries must not duplicate animals, lots or vaccines.
- External/native app API lives under `/api/public/app/*` (`src/lib/app-api.server.ts`), each handler verifies the bearer and acts as the user so RLS applies — why: public prefix bypasses site auth, so authorization must be per-handler.
- Offline app shell uses vite-plugin-pwa registered only via `src/lib/pwa-register.ts` (never in dev/preview/iframe, `?sw=off` kill switch) — why: service workers in preview serve stale builds.
- Shared visual styling lives in src/styles.css; motion targets headings and interactive controls, never entire tables or all rows, and respects reduced motion — why: consistent presentation without adding cost to large datasets.
- Assinatura: o site só cria a cobrança; quem libera o Premium é o aviso do Mercado Pago, com assinatura HMAC conferida em `src/lib/mercadopago.ts` e aplicada por `mp_*` (service role) — why: o navegador nunca pode decidir que um pagamento foi aprovado.
- eBooks: o PDF sai por `/api/ebooks/$id/arquivo`, que confere assinatura, registra o acesso e repassa um link assinado de 60s; o leitor desenha em canvas com marca d'água — why: o arquivo não pode virar link público nem cair no cache do navegador.
- Indicadores e avisos usam uma função SECURITY INVOKER por tela (`indicadores_propriedade`, `central_avisos`, `agenda_periodo`) — why: uma leitura só, com as regras de acesso de quem olha.
- Tudo que o administrador publica (eBook, APK, imagens) vai para bucket privado com política de escrita só para `administrador` e leitura para `authenticated` — why: conteúdo pago ou interno nunca fica em URL pública.
- QR Code é gerado por `src/lib/qr.ts` (versões 1–10, correção M), sem dependência nova — why: o registro npm não está acessível no ambiente de desenvolvimento.
- Visual: nada abaixo de 14px, sem CAIXA ALTA em rótulo, sem cor fixa em hex no JSX (use os tokens de src/styles.css) e sem `dark` preso em diálogo ou menu — why: o site é usado no sol, no celular, e tem tema claro e escuro.
- As 39 áreas vindas do aplicativo moram em `src/components/app/modulos-aplicativo.ts` (gerado do registro de módulos do APK) e entram no site por `modules` e `IMPLEMENTADAS` em `ApecuariaApp.tsx`; o menu monta cada item com `doApp()` em `casca/navegacao.ts` — why: rótulo, ícone, frase e campos ficam num lugar só e não divergem do aplicativo.
- Campo `type:"ref"` liga a qualquer cadastro da propriedade (`refTabela`, `refRotulo`, `refCriar`, `refOnde`); sem `refCriar` o cadastro precisa existir antes e a mensagem diz onde fazê-lo — why: criar um plantio ou uma máquina a partir de um nome solto inventaria dados que ninguém conferiu.
- Campo `type:"sim"` grava verdadeiro/falso de verdade (converte em `RecordDialog`), e `padrao` preenche o campo no registro novo — why: coluna booleana não aceita o texto "true" e registro novo sem padrão nasce sem situação.
- SQL das áreas do aplicativo documentado em `docs/sql/2026-11-08-modulos-do-aplicativo.sql`, idempotente e na ordem de dependência — why: o banco de produção precisa poder ser recriado igual.
- As chaves do Mercado Pago e a de resgate são lidas por `lerChave` (`src/lib/chaves.server.ts`): primeiro a do painel do administrador (cifrada no banco com a chave mestra), depois a do ambiente — why: o administrador troca a chave sem depender de quem configura o servidor, e nenhum segredo chega ao navegador.
- `central_avisos` também olha as áreas novas: carência do leite (`tratamentos.carencia_leite`), retorno de tratamento, tarefa atrasada, conta a pagar da semana e documento vencendo — why: a área só serve se o que está vencendo aparecer no Início sem ninguém ir procurar.
- Hospedagem própria: a compilação alvo é servidor Node (nitro `node-server`), não Cloudflare; o IP de quem acessa vem do último endereço de `x-forwarded-for`, contando `PROXIES_CONFIAVEIS` servidores nossos na frente — why: o cabeçalho da Cloudflare não existe fora dela e, sem isso, todo mundo vira o mesmo IP e o site se bloqueia sozinho.
- Banco em MySQL: esquema gerado por `banco/mysql/gerar.py` a partir do que foi extraído do PostgreSQL; data e hora sempre em UTC e coluna de data sem valor padrão do banco — why: o MySQL não guarda fuso e o padrão do servidor (UTC) jogaria a anotação da noite para o dia seguinte.
- `src/lib/dados/escopos.ts` é GERADO por `banco/mysql/escopos.py` e diz o dono de cada tabela; toda leitura e gravação passa por `src/lib/dados/acesso.ts`, que monta a condição a partir do escopo — why: o MySQL não tem regra de acesso no banco, então a separação entre fazendas vive no servidor, num lugar só, e tabela sem escopo é recusada em vez de liberada.
- Pessoa sem nenhuma fazenda recebe a condição `1 = 0`, nunca uma condição vazia — why: lista vazia virando `IN ()` ou sumindo abriria o banco inteiro.
- Código de 2 fatores em `src/lib/conta/totp.ts`, sem dependência, conferido contra os seis exemplos da RFC 6238 — why: se o cálculo divergir, o aplicativo de códigos do celular deixa de abrir o site.
- `dashboard_resumo` e `central_avisos` do banco novo vivem em `src/lib/dados/resumo.server.ts` e `src/lib/dados/avisos.server.ts`, com as MESMAS 18 chaves e as mesmas chaves de aviso do banco antigo — why: o Início, a Yui e a rota do aplicativo leem por nome, e a chave do aviso é o que guarda o "já vi isso": mudar o formato faria tudo que foi dispensado voltar a aparecer.
- A situação de cada vacinação sai de `ULTIMAS_DOSES` (`src/lib/dados/vacinas.server.ts`), que refaz a visão `v_vacinacoes_status` com `ROW_NUMBER()` por propriedade + vacina + animal (ou lote) — why: o MySQL não tem a visão, e sem a regra da última dose a mesma vacina cobraria reforço várias vezes.
- No servidor a data de hoje vem de `dataNoFuso()`, nunca de `dataLocalISO()` nem do `CURDATE()` do banco, e mês com coluna de data e hora usa `inicioDoDiaNoFuso()` — why: o relógio do servidor é UTC, e depois das 21h o "hoje" viraria amanhã e as três primeiras horas do mês cairiam no mês anterior.
- `agenda_periodo` do banco novo está em `src/lib/dados/agenda.server.ts`: sete tipos de compromisso (vacina, parto, cio, tarefa, retorno, conta, revisão de máquina), teto de 500 eventos com `truncado`, e período recusado acima de 400 dias ou de trás para frente — why: a tela agrupa por dia e deixa esconder tipo por tipo, e um ano de fazenda grande não cabe numa lista rolável.
- `indicadores_propriedade` do banco novo está em `src/lib/dados/indicadores.server.ts`: número sem base é `null`, nunca zero, e valor fora do possível (intervalo entre partos fora de 250–900 dias, idade ao primeiro parto fora de 400–2200, pesagens com menos de 20 dias entre elas) é descartado, não corrigido — why: travessão e zero dizem coisas diferentes para o produtor, e um erro de digitação entrando na média estraga o número de toda a fazenda.
- Janela dos indicadores em mês de calendário (`mesesAntes()`), não em 365 dias — why: é o que o banco antigo fazia, e a diferença aparece em ano bissexto.
- Apagar uma fazenda passa por `apagarPropriedade` (em `repositorio.server.ts`), que apaga na `ORDEM_DE_EXCLUSAO` gerada em `escopos.ts`, numa transação — why: o PostgreSQL conferia as referências no fim da operação, o MySQL confere na hora, e um DELETE direto na fazenda esbarra em `nascimentos`, que aponta para `animais`.
- `sou_assinante` e `minha_area_assinante` olham só a ÚLTIMA assinatura de cada propriedade (`assinante.server.ts`) — why: renovar não apaga a anterior, então contar todas faria uma assinatura cancelada e depois renovada aparecer como cancelada, e uma renovada três vezes aparecer como três.
- Nome de tabela nunca vem do pedido: `relatorios.server.ts` tem as listas fixas (`TABELAS_DO_DIAGNOSTICO`, `TABELAS_DO_APLICATIVO`) e compara o que chegou contra elas — why: as funções antigas montavam o nome com `format('%I')`, e aceitar o nome de fora seria convite a pedir qualquer outra tabela.
- A marca de sincronização do aplicativo é o par (updated_at, id), nunca só a data — why: duas linhas salvas no mesmo milésimo existem, e com só a data o aplicativo pularia uma ou baixaria a mesma para sempre.
- Em `seg_registrar_incidente`, de quem é o incidente vem de `quem.userId`, e bloquear é decisão do servidor (nunca do pedido) — why: senão qualquer pessoa registraria incidente e bloqueio no nome de outra.
- Bloqueio de acesso: o `on conflict (tipo, valor) where ativo` do PostgreSQL virou ler-e-decidir dentro de uma transação (`seguranca-banco.server.ts`) — why: o MySQL não tem índice único com condição.
- `Quem` carrega `aal` (passou por 2FA nesta sessão) e `sessaoId`; ausente vale como "aal1" — why: ligar a exigência de 2FA para todos os administradores só pode ser feito por quem já usa 2FA, senão a pessoa se tranca do lado de fora.
- Toda mudança de plano pelo painel grava em `plano_auditoria` na mesma transação (`admin.server.ts`) — why: um Premium aparecendo do nada sem saber de quem partiu é problema de segurança, não de registro.
- As visões do banco antigo estão em `banco/mysql/visoes.sql`, escritas à mão (visão é regra, não estrutura), e são SÓ LEITURA: `SOMENTE_LEITURA` em `escopos.ts` recusa gravação com mensagem clara — why: resumo não se grava, altera-se o lançamento que o alimenta.
- `v_vacinacoes_status` NÃO foi refeita como visão: ela depende de "hoje em Brasília" e visão não recebe parâmetro. Quem calcula é `vacinas.server.ts` — why: duas versões da mesma regra divergem com o tempo.
- As telas que só leem e gravam tabela já importam `dados` de `@/lib/dados` (13 arquivos); as que usam login, arquivos ou tempo real continuam no cliente antigo até as etapas 3 e 5 — why: trocar tudo de uma vez derrubaria o login antes de existir o novo.
- E-mail sai por SMTPS (TLS desde o primeiro byte, porta 465) em `src/lib/conta/email.server.ts`, escrito sobre `node:tls` sem biblioteca, e com o certificado conferido — why: STARTTLS começa em claro, e é nessa troca que a senha da conta de e-mail pode escapar; e o registro de pacotes não está acessível no ambiente de desenvolvimento.
- Pedir recuperação de senha responde igual para e-mail que existe e que não existe (`recuperacao.server.ts`), o token é guardado só como resumo sha256, o link vale 1h e serve uma vez, e usá-lo derruba todas as sessões — why: respostas diferentes viram lista de quem tem conta aqui, e quem troca a senha por desconfiança precisa que o invasor saia.
- O link de recuperação é montado com o endereço que a ROTA informa, nunca com o cabeçalho `Host` do pedido — why: senão qualquer um manda para a vítima um e-mail nosso apontando para o site dele.
- Sem `select` aninhado no caminho novo: quando a tela precisa de dado de outra tabela, faz uma segunda leitura e junta em JavaScript — why: o servidor confere tabela e coluna uma por uma, e junção vinda do navegador seria uma linguagem a mais para conferir (hoje havia exatamente um caso, no Início).
- Entrada pelo Google (`google.server.ts`): o `state` é assinado E guardado num cookie, e a volta exige os dois iguais — why: só sortear o valor não protege; o que protege é ele ter voltado no mesmo navegador que começou, senão alguém prepara um "retorno" e faz a vítima entrar com a conta do atacante.
- Ligar uma identidade Google a uma conta que já existe só acontece com `email_verified` do Google — why: a ligação é por e-mail, e aceitar e-mail não confirmado deixaria qualquer um criar uma conta Google com o endereço de um produtor e entrar como ele.
- `/api/conta/entrar` dá a mesma mensagem para e-mail inexistente e senha errada, e limita por e-mail E por IP — why: mensagens diferentes entregam quem tem conta aqui; um limite só por e-mail cai para uma lista de e-mails, e só por IP cai para quem tem vários endereços.
- `/api/conta/recuperar` responde 200 sempre, inclusive quando o envio falha; o erro vai só para o registro do servidor — why: a resposta não pode dizer quem tem conta no site.
- `routeTree.gen.ts` é mantido À MÃO neste projeto: toda rota nova precisa das 7 inserções (import, update, 3 mapas de tipo, 3 uniões, filhos da raiz, objeto de rotas, registro de tipos) — why: o gerador do TanStack não roda aqui, e meia inserção quebra a compilação.
- Os arquivos (eBooks, APK, imagens) ficam numa pasta FORA de `public_html`, apontada por `ARQUIVOS_DIR`, e só saem por rota nossa — why: o que está em public_html o Apache serve direto, sem passar pelo nosso código, e eBook é pago: um endereço adivinhado valeria uma assinatura.
- `caminhoReal()` em `arquivos/armazem.server.ts` resolve o caminho e exige que o resultado continue dentro da pasta do balde (não procura ".." no texto), e recusa byte nulo — why: `a/../../b` não tem ".." no fim, `%2e%2e` já chega decodificado, e `foto.png\0.php` é um nome na conferência e outro no disco.
- O link de arquivo é assinado sobre balde + caminho + prazo juntos, com teto de 1h — why: assinar só o caminho deixa esticar o prazo, assinar só o prazo deixa trocar o arquivo, e link vaza para histórico e registro de servidor alheio.
- Nos baldes de pessoa e de fazenda (`profile-avatars`, `property-*`), a PRIMEIRA PASTA do caminho é o dono, e `podeGravar()` em `arquivos/api.server.ts` confere isso — why: sem essa conferência, qualquer pessoa que entrou gravaria em `profile-avatars/<id de outra>/avatar.webp` e trocaria a foto de quem quisesse.
- O tipo entregue por `/api/arquivos` vem da extensão E precisa estar na lista do balde — why: um arquivo que entrou de outro jeito não pode sair como imagem, e `nosniff` sozinho não basta se nós mesmos declararmos o tipo errado.
- O PDF do eBook nunca ganha link, nem assinado: a rota dos eBooks lê o arquivo direto (`pedacoDoArquivo`) depois de conferir a assinatura e registrar o acesso — why: link, mesmo curto, é um endereço que se repassa.
- `src/lib/arquivos/index.ts` usa a MESMA variável `VITE_BANCO` do banco — why: é o banco que guarda o caminho de cada arquivo, e duas variáveis separadas deixariam apontar uma para cada lado e procurar na pasta nova um caminho que só existe no banco antigo.
- As telas não recebem o valor do cookie de sessão. Quando precisam de Bearer para as nossas rotas, usam o token curto de `conta/token-curto.ts`: 5 minutos, assinado por HMAC, guardado em lugar nenhum, e cunhado só por quem tem o cookie — why: o cookie é HttpOnly para que um script injetado não consiga usar a sessão de outro lugar, e devolver o valor dele ao JavaScript desfaria isso.
- O token curto carrega SÓ o identificador da pessoa, nunca "é administrador" — why: quem é administrador sai do banco em cada pedido; um token cunhado antes de alguém perder o cargo continuaria dizendo que ele é.
- `exigirUsuario()` aceita os dois formatos de Bearer (Supabase e o nosso) — why: é o que deixa trocar as telas uma a uma em vez de derrubar de uma vez as oito rotas que leem Bearer.
- `src/lib/conta/index.ts` entrega a sessão às telas pela mesma chave `VITE_BANCO` do banco e dos arquivos — why: o login novo grava sessão no banco novo, e apontar sessão e dados para lados diferentes deixaria a pessoa entrar num lugar e os dados dela estarem no outro.
- O atalho de sessão guarda a resposta de `/api/conta/eu` enquanto o token vale e junta chamadas simultâneas numa ida só; renova 30s ANTES de vencer — why: as telas chamam getUser/getSession em 34 lugares sem combinar entre si, e esperar o vencimento daria um pedido falhando no meio de um clique.
- `signOut()` esquece a sessão local ANTES de o servidor responder — why: continuar achando que a pessoa está dentro até a resposta chegar mostra dados de uma sessão que já acabou.
- As rotas de servidor (`*.server.ts`, `start.ts`, `integrations/supabase/*`, `routes/api/public/app/*`) continuam no cliente Supabase direto, de propósito: os atalhos `dados`/`sessao`/`armazem` falam com a nossa API pelo navegador e não servem do lado do servidor.
- "Qualquer um destes" (`qualquerDe` no servidor, `qualquerIgual()` no cliente) existe para perguntas como "as crias deste animal" (mãe OU pai). Recebe coluna e valor, nunca um texto de consulta — why: o `or` do cliente antigo recebia um padrão escrito no navegador, e aceitar isso seria mais uma linguagem para conferir.
- `select(colunas, { head: true })` traz só a contagem — why: o painel mostra "3 pedidos abertos" sem ninguém ler os registros, e trazer as linhas para contá-las é trabalho jogado fora.
- ARMADILHA RECORRENTE: antes de trocar o import de uma tela, procure variável local chamada `dados`, `sessao` ou `armazem`. Já aconteceu três vezes (Início, leitor de eBook, SuporteAdmin): a local cobre o import e a consulta passa a depender de si mesma, o que aparece como erro de tipo circular e não como erro de nome.
- Ordem sem direção é CRESCENTE (`crescente === false ? "DESC" : "ASC"`) — why: é o padrão do SQL e o do cliente antigo; tratar a ausência como decrescente devolvia a lista ao contrário sem erro nenhum, e só apareceu porque uma conferência comparou a ordem.
- 2FA: o segredo é cifrado no banco com a chave mestra, o fator só vale depois de confirmado, cada código vale UMA vez (o intervalo aceito fica em `fatores_2fa.ultimo_contador`), e tirar a verificação exige um código válido — why: sem o último, quem roubasse uma sessão desligaria a segunda etapa e ficaria com a conta.
- Trocar a senha exige ter digitado a atual há pouco NESTA sessão: conferir deixa `sessoes.senha_conferida_em`, e `/api/conta/senha` ação "trocar" exige essa marca recente e a gasta — why: antes a ordem era combinada entre as telas, e quem chamasse só a segunda trocava a senha sem saber a primeira; com sessão em cookie isso viraria a conta inteira.
- Com 2FA ligado, trocar a senha exige sessão `aal2` — why: senão a segunda etapa protege a entrada e não protege a troca, que é o que dá a conta de vez a quem já estiver dentro.
- `src/lib/conta/index.ts` repassa o cliente antigo método a método, nunca com `{ ...supabase.auth }` — why: os métodos dele contam com o próprio dono, e espalhados quebram no clique, não na compilação.
